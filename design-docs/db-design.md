# Database Design - AI Career Helper

## 1. Goal

This document defines the target normalized SQLite database design for the AI Career Helper backend.

The current implementation stores data in `store_buckets(name, value)` as JSON buckets. That is acceptable for a small local persistent store, but the target design below moves business data into explicit relational tables so the database can be queried, indexed, constrained, and managed with normal SQLite tools.

## 2. Design Principles

- Use SQLite as the local database engine.
- Keep API response contracts unchanged. The repository layer should assemble camelCase API responses from snake_case database columns.
- Normalize high-value entities and relationships: users, catalogs, goals, jobs, applications, meetings, notifications, interview records.
- Keep small ordered lists in child tables when they need querying or editing, such as job skills, profile skills, catalog goal skills, tracking steps, and notification ownership.
- Keep LLM/generated large structured payloads as JSON where relational querying is not needed, such as profile extraction drafts and scoring dimensions.
- Store timestamps as Unix milliseconds (`INTEGER`) unless a field is already API-defined as a string, such as job `posted` or goal `last_updated`.
- Use `TEXT` ids generated by the app (`u_...`, `g_...`, `j_...`) to preserve existing API behavior.
- Enforce ownership with `user_id` foreign keys on all user-owned resources.

## 4. Core Schema

### 4.1 Users And Auth

```sql
CREATE TABLE users (
  id TEXT PRIMARY KEY,
  email TEXT NOT NULL UNIQUE COLLATE NOCASE,
  name TEXT NOT NULL,
  password_hash TEXT NOT NULL,
  created_at INTEGER NOT NULL
);

CREATE TABLE refresh_tokens (
  jti TEXT PRIMARY KEY,
  user_id TEXT NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  created_at INTEGER NOT NULL,
  expires_at INTEGER,
  revoked_at INTEGER
);

CREATE INDEX idx_refresh_tokens_user_id ON refresh_tokens(user_id);
```

Notes:

- `email_index` is removed because `users.email` is indexed and unique.
- Logout can delete a refresh token or set `revoked_at`; deleting is closest to current behavior.

### 4.2 Profiles

```sql
CREATE TABLE profiles (
  user_id TEXT PRIMARY KEY REFERENCES users(id) ON DELETE CASCADE,
  name TEXT NOT NULL,
  updated_at INTEGER NOT NULL
);

CREATE TABLE profile_education (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  user_id TEXT NOT NULL REFERENCES profiles(user_id) ON DELETE CASCADE,
  sort_order INTEGER NOT NULL,
  degree TEXT NOT NULL DEFAULT '',
  school TEXT NOT NULL DEFAULT '',
  major TEXT NOT NULL DEFAULT '',
  grade REAL,
  start TEXT NOT NULL DEFAULT '',
  end TEXT
);

CREATE TABLE profile_internships (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  user_id TEXT NOT NULL REFERENCES profiles(user_id) ON DELETE CASCADE,
  sort_order INTEGER NOT NULL,
  title TEXT NOT NULL DEFAULT '',
  company TEXT NOT NULL DEFAULT '',
  start TEXT NOT NULL DEFAULT '',
  end TEXT,
  description TEXT NOT NULL DEFAULT ''
);

CREATE TABLE profile_projects (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  user_id TEXT NOT NULL REFERENCES profiles(user_id) ON DELETE CASCADE,
  sort_order INTEGER NOT NULL,
  title TEXT NOT NULL DEFAULT '',
  start TEXT NOT NULL DEFAULT '',
  end TEXT,
  description TEXT NOT NULL DEFAULT ''
);

CREATE TABLE profile_skills (
  user_id TEXT NOT NULL REFERENCES profiles(user_id) ON DELETE CASCADE,
  skill TEXT NOT NULL,
  sort_order INTEGER NOT NULL,
  PRIMARY KEY (user_id, skill)
);

CREATE TABLE profile_coursework (
  user_id TEXT NOT NULL REFERENCES profiles(user_id) ON DELETE CASCADE,
  course TEXT NOT NULL,
  sort_order INTEGER NOT NULL,
  PRIMARY KEY (user_id, course)
);
```

Notes:

- Profile is one-to-one with user.
- Ordered child records preserve current API list order.
- Empty internships should still be filtered in service code before inserting.

### 4.3 CV Extraction And Onboarding

```sql
CREATE TABLE cv_extract_tasks (
  id TEXT PRIMARY KEY,
  user_id TEXT NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  status TEXT NOT NULL CHECK (status IN ('processing', 'complete', 'failed')),
  stage TEXT NOT NULL,
  draft_json TEXT,
  polls INTEGER NOT NULL DEFAULT 0,
  error TEXT,
  created_at INTEGER NOT NULL,
  updated_at INTEGER NOT NULL
);

CREATE INDEX idx_cv_extract_tasks_user_id ON cv_extract_tasks(user_id);

CREATE TABLE onboarding_chat_sessions (
  id TEXT PRIMARY KEY,
  user_id TEXT NOT NULL UNIQUE REFERENCES users(id) ON DELETE CASCADE,
  status TEXT NOT NULL CHECK (status IN ('in_progress', 'complete')),
  question TEXT,
  question_index INTEGER NOT NULL,
  total_questions INTEGER NOT NULL,
  answers_json TEXT NOT NULL DEFAULT '{}',
  draft_json TEXT,
  created_at INTEGER NOT NULL,
  updated_at INTEGER NOT NULL
);

CREATE TABLE onboarding_chat_turns (
  id TEXT PRIMARY KEY,
  session_id TEXT NOT NULL REFERENCES onboarding_chat_sessions(id) ON DELETE CASCADE,
  role TEXT NOT NULL CHECK (role IN ('assistant', 'user')),
  text TEXT NOT NULL,
  timestamp INTEGER NOT NULL,
  sort_order INTEGER NOT NULL
);

CREATE INDEX idx_onboarding_turns_session ON onboarding_chat_turns(session_id, sort_order);
```

Notes:

- `answers_json` and `draft_json` are retained as JSON because they are transient AI/workflow state.
- Current behavior allows at most one resumable onboarding session per user.

## 5. Public Catalogs

### 5.1 Career Goal Catalog

```sql
CREATE TABLE catalog_goals (
  id TEXT PRIMARY KEY,
  title TEXT NOT NULL,
  description TEXT NOT NULL,
  color TEXT NOT NULL,
  default_status TEXT NOT NULL CHECK (default_status IN ('active', 'exploring')),
  sort_order INTEGER NOT NULL DEFAULT 0
);

CREATE TABLE catalog_goal_match_signals (
  catalog_goal_id TEXT NOT NULL REFERENCES catalog_goals(id) ON DELETE CASCADE,
  signal TEXT NOT NULL,
  sort_order INTEGER NOT NULL,
  PRIMARY KEY (catalog_goal_id, signal)
);

CREATE TABLE catalog_core_skills (
  id TEXT PRIMARY KEY,
  catalog_goal_id TEXT NOT NULL REFERENCES catalog_goals(id) ON DELETE CASCADE,
  name TEXT NOT NULL,
  description TEXT NOT NULL,
  default_status TEXT NOT NULL,
  sort_order INTEGER NOT NULL
);

CREATE INDEX idx_catalog_core_skills_goal ON catalog_core_skills(catalog_goal_id, sort_order);

CREATE TABLE catalog_skill_steps (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  skill_id TEXT NOT NULL REFERENCES catalog_core_skills(id) ON DELETE CASCADE,
  step_index INTEGER NOT NULL,
  text TEXT NOT NULL,
  UNIQUE (skill_id, step_index)
);

CREATE TABLE catalog_skill_resources (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  skill_id TEXT NOT NULL REFERENCES catalog_core_skills(id) ON DELETE CASCADE,
  resource_index INTEGER NOT NULL,
  title TEXT NOT NULL,
  type TEXT NOT NULL,
  url TEXT NOT NULL,
  UNIQUE (skill_id, resource_index)
);

CREATE TABLE catalog_skill_job_keywords (
  skill_id TEXT NOT NULL REFERENCES catalog_core_skills(id) ON DELETE CASCADE,
  keyword TEXT NOT NULL,
  sort_order INTEGER NOT NULL,
  PRIMARY KEY (skill_id, keyword)
);
```

## 6. User Goals And Tracking

```sql
CREATE TABLE user_goals (
  id TEXT PRIMARY KEY,
  user_id TEXT NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  catalog_id TEXT NOT NULL REFERENCES catalog_goals(id),
  title TEXT NOT NULL,
  description TEXT NOT NULL,
  color TEXT NOT NULL,
  status TEXT NOT NULL CHECK (status IN ('active', 'exploring')),
  progress INTEGER NOT NULL DEFAULT 0 CHECK (progress BETWEEN 0 AND 100),
  last_updated TEXT NOT NULL,
  created_at INTEGER NOT NULL,
  sort_order INTEGER NOT NULL,
  UNIQUE (user_id, catalog_id)
);

CREATE INDEX idx_user_goals_user_order ON user_goals(user_id, sort_order);

CREATE TABLE user_goal_confidence (
  goal_id TEXT NOT NULL REFERENCES user_goals(id) ON DELETE CASCADE,
  skill_id TEXT NOT NULL REFERENCES catalog_core_skills(id),
  score INTEGER NOT NULL CHECK (score BETWEEN 1 AND 5),
  PRIMARY KEY (goal_id, skill_id)
);

CREATE TABLE goal_tracking (
  goal_id TEXT PRIMARY KEY REFERENCES user_goals(id) ON DELETE CASCADE,
  week_started_at INTEGER NOT NULL
);

CREATE TABLE goal_tracking_modules (
  goal_id TEXT NOT NULL REFERENCES goal_tracking(goal_id) ON DELETE CASCADE,
  skill_id TEXT NOT NULL REFERENCES catalog_core_skills(id),
  steps_completed_since_rerate INTEGER NOT NULL DEFAULT 0,
  rerate_dismissed INTEGER NOT NULL DEFAULT 0 CHECK (rerate_dismissed IN (0, 1)),
  PRIMARY KEY (goal_id, skill_id)
);

CREATE TABLE goal_tracking_completed_steps (
  goal_id TEXT NOT NULL,
  skill_id TEXT NOT NULL,
  step_index INTEGER NOT NULL,
  PRIMARY KEY (goal_id, skill_id, step_index),
  FOREIGN KEY (goal_id, skill_id)
    REFERENCES goal_tracking_modules(goal_id, skill_id)
    ON DELETE CASCADE
);

CREATE TABLE goal_tracking_consumed_resources (
  goal_id TEXT NOT NULL,
  skill_id TEXT NOT NULL,
  resource_index INTEGER NOT NULL,
  PRIMARY KEY (goal_id, skill_id, resource_index),
  FOREIGN KEY (goal_id, skill_id)
    REFERENCES goal_tracking_modules(goal_id, skill_id)
    ON DELETE CASCADE
);

CREATE TABLE goal_tracking_week_focus (
  goal_id TEXT NOT NULL REFERENCES goal_tracking(goal_id) ON DELETE CASCADE,
  focus TEXT NOT NULL,
  sort_order INTEGER NOT NULL,
  PRIMARY KEY (goal_id, focus)
);
```

Notes:

- `user_goals` duplicates `title`, `description`, and `color` from the catalog at creation time. This preserves current API behavior if catalog text changes later.
- `UNIQUE (user_id, catalog_id)` enforces `GOAL_ALREADY_ADDED`.

## 7. Jobs, Saved Jobs, And Applications

```sql
CREATE TABLE saved_jobs (
  user_id TEXT NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  goal_id TEXT NOT NULL REFERENCES user_goals(id) ON DELETE CASCADE,
  job_id TEXT NOT NULL REFERENCES jobs(id) ON DELETE CASCADE,
  saved_at INTEGER NOT NULL,
  PRIMARY KEY (user_id, goal_id, job_id)
);

CREATE INDEX idx_saved_jobs_goal ON saved_jobs(goal_id);

CREATE TABLE applications (
  id TEXT PRIMARY KEY,
  user_id TEXT NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  kind TEXT NOT NULL CHECK (kind IN ('partner', 'standard')),
  goal_id TEXT NOT NULL REFERENCES user_goals(id) ON DELETE CASCADE,
  job_id TEXT NOT NULL REFERENCES jobs(id),
  title TEXT NOT NULL,
  company TEXT NOT NULL,
  submitted_at INTEGER NOT NULL,
  partner_status TEXT CHECK (
    partner_status IS NULL OR partner_status IN (
      'referral_sent', 'under_review', 'interview', 'final_round', 'offer_extended'
    )
  ),
  manual_status TEXT CHECK (
    manual_status IS NULL OR manual_status IN (
      'applied', 'screening', 'interview', 'offer', 'rejected', 'withdrawn'
    )
  ),
  cv_text TEXT,
  UNIQUE (user_id, job_id)
);

CREATE INDEX idx_applications_user_submitted ON applications(user_id, submitted_at DESC);
CREATE INDEX idx_applications_goal ON applications(goal_id);
```

Notes:

- `UNIQUE (user_id, job_id)` enforces `ALREADY_APPLIED`.
- `title` and `company` are snapshotted onto the application, matching current behavior.
- Service code should enforce that `kind='partner'` only uses exclusive jobs.

```sql
  alumni_id TEXT NOT NULL REFERENCES alumni(id),

CREATE UNIQUE INDEX ux_meetings_one_pending_per_alumni

  meeting_id TEXT NOT NULL REFERENCES meetings(id) ON DELETE CASCADE,
  preferred_time TEXT NOT NULL,

```

Notes:

- The partial unique index enforces the current `MEETING_ALREADY_PENDING` behavior.

## 10. Notifications

```sql
CREATE TABLE notifications (
  id TEXT PRIMARY KEY,
  user_id TEXT NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  type TEXT NOT NULL CHECK (type IN ('system', 'job', 'alumni', 'meeting', 'milestone', 'week')),
  severity TEXT NOT NULL CHECK (severity IN ('info', 'success', 'warning')),
  title TEXT NOT NULL,
  body TEXT NOT NULL,
  link TEXT,
  created_at INTEGER NOT NULL,
  read INTEGER NOT NULL DEFAULT 0 CHECK (read IN (0, 1)),
  dedup_key TEXT,
  UNIQUE (user_id, dedup_key)
);

CREATE INDEX idx_notifications_user_created ON notifications(user_id, created_at DESC);
CREATE INDEX idx_notifications_user_read ON notifications(user_id, read, created_at DESC);
```

Notes:

- SQLite allows multiple `NULL` values in a unique index, so `UNIQUE (user_id, dedup_key)` still permits notifications without a dedup key.
- The service should keep the most recent 50 notifications per user, as the current implementation does.

## 11. Recommended Repository API

Routers should stop mutating `store.users[...]` and other dictionaries directly. The normalized database should be accessed through explicit repository methods. Suggested method groups:

### Auth

- `create_user(name, email, password_hash) -> UserRecord`
- `get_user_by_id(user_id) -> UserRecord | None`
- `get_user_by_email(email) -> UserRecord | None`
- `save_refresh_token(jti, user_id, expires_at)`
- `delete_refresh_token(jti)`
- `delete_user(user_id)`

### Catalogs

- `list_catalog_goals(profile=None) -> list[CatalogGoal]`
- `get_catalog_goal(catalog_id) -> CatalogGoal | None`
- `list_jobs(filters, pagination) -> JobListPage`
- `get_job(job_id) -> JobListing | None`
- `list_alumni(filters) -> list[AlumniProfile]`
- `get_alumni(alumni_id) -> AlumniProfile | None`

### User Data

- `get_profile(user_id)`
- `upsert_profile(user_id, profile_input)`
- `list_user_goals(user_id)`
- `create_user_goal(user_id, catalog_id)`
- `update_user_goal(user_id, goal_id, patch)`
- `delete_user_goal(user_id, goal_id)`
- `get_tracking(user_id, goal_id)`
- `update_tracking_step(...)`
- `update_tracking_resource(...)`
- `set_week_focus(...)`

### Applications And Coaching

- `list_applications(user_id, goal_id=None)`
- `create_application(user_id, kind, goal_id, job_id, cv_text=None)`
- `update_application_status(user_id, application_id, manual_status)`
- `delete_application(user_id, application_id)`
- `create_interview_review(...)`
- `get_interview_review(...)`
- `create_mock_session(...)`
- `append_mock_turn(...)`

### Meetings And Notifications

- `create_meeting(user_id, alumni_id, topic, message, preferred_times)`
- `update_meeting_status(user_id, meeting_id, status)`
- `push_notification(user_id, ...)`
- `list_notifications(user_id, unread=None, limit=20, cursor=None)`
- `mark_notifications_read(user_id, ids=None)`

## 12. Migration Plan From `store_buckets`

1. Create the normalized schema in a new migration script, for example `migrations/001_normalized_schema.sql`.
2. Read existing `store_buckets` rows from `career_helper.sqlite3`.
3. Insert public catalogs first:
   - `goal_catalog` -> `catalog_goals` and catalog child tables.
   - `jobs` -> `jobs`, `job_skills`.
   - `alumni` -> `alumni`, alumni child tables.
4. Insert auth data:
   - `users` -> `users`.
   - `refresh_jti` -> `refresh_tokens`.
5. Insert user-owned data in dependency order:
   - `profiles`
   - `goals`
   - `tracking`
   - `saved_jobs`
   - `applications`
   - `reviews`
   - `mocks`
   - `meetings`
   - `notifications`
6. Keep `store_buckets` temporarily as `legacy_store_buckets` or leave it untouched until verification is complete.
7. Run the existing smoke tests against the repository-backed implementation.
8. After verification, remove the JSON bucket code path.

## 13. Open Decisions

- Whether `profile_education`, `profile_internships`, and `profile_projects` need stable public ids. Current API does not expose ids, so `AUTOINCREMENT` internal ids are enough.
- Whether `interview_reviews.dimensions_json` should later be split into `interview_review_dimensions`. Split it only if the UI needs filtering or reporting across dimension scores.
- Whether `jobs.posted` should remain a string or become a Unix timestamp. Current API uses a string, so this design keeps it as `TEXT`.
- Whether deleted applications should be hard-deleted or soft-deleted. Current API hard-deletes.
- Whether catalog edits should preserve historical application and user goal snapshots. This design snapshots user goal title/color/description and application title/company.

## 14. Minimal First Implementation Scope

For the next implementation step, use this order:

1. Add schema migration creation.
2. Implement read-only normalized public catalogs: `catalog_goals`, `jobs`, `alumni`.
3. Move `users`, `refresh_tokens`, and `profiles`.
4. Move `user_goals`, `tracking`, `saved_jobs`, and `applications`.
5. Move coaching, meetings, notifications, and background task state.

This order keeps each phase testable and avoids changing all routers at once.
